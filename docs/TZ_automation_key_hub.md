# ТЗ: automation_key — единая генерация в gmail-mcp, выбор области действия

**Статус:** уточнение владельца 2026-08-11, поверх `docs/TZ/TZ_temp_automation_key.md` и `docs/TZ/TZ_multi_automation_windows.md`.

## Зачем и что меняется

Владелец объяснил (2026-08-11): временный `automation_key` должен быть
**один механизм на всю экосистему MCP-серверов**, а не отдельный на каждый.
Генерация — через кнопки в Telegram: жмёшь кнопку → появляется выбор из
восьми: по одной кнопке на каждый из 6 сервисов (gmail, calendar, drive,
sheets, docs, ticktick) + «Все сразу» + «Получить ключ». Тыкаешь нужные
сервисы (✗ → ✓ при нажатии, можно несколько), жмёшь «Получить ключ» —
получаешь ОДИН ключ, действующий именно на отмеченные сервисы (не
обязательно все).

**Почему генерация живёт в gmail-mcp, а не в ticktick-mcp.** После
консолидации ботов (2026-08-10/11) единственный вебхук Telegram
зарегистрирован у gmail-mcp — остальные пять сервисов (включая ticktick-mcp)
свой вебхук больше не держат. Только gmail-mcp физически получает
апдейты от кнопок в реальном времени, поэтому весь интерактивный флоу
(показ кнопок, накопление выбора, генерация) обязан жить там.

**Разделение ответственности:**
- **gmail-mcp** — владеет ВСЕЙ генерацией/отзывом/списком: UI кнопок,
  накопление текущего выбора между нажатиями, запись новой строки в общую
  таблицу, отправка ключа владельцу, самоудаление сообщения с ключом через
  10с.
- **Каждый MCP-сервис** (в этом ТЗ — только ticktick-mcp, остальные четыре
  отдельным заходом) — ТОЛЬКО читает общую таблицу и проверяет: подходит ли
  присланный `automation_key` для МЕНЯ (моё имя есть в `scope`, или
  `scope='all'`, окно не отозвано и не истекло). Ничего не пишет в эту
  таблицу и не показывает никаких кнопок про неё.

## Общая схема (обе стороны обязаны совпадать буквально)

Таблица `tg_automation_windows`, тот же `CONSENT_DATABASE_URL`, что и у
`tg_approvals`/`mcp_manifests` (общий для gmail/calendar/drive/sheets/docs/
ticktick-mcp).

```sql
CREATE TABLE IF NOT EXISTS tg_automation_windows (
    window_id       TEXT PRIMARY KEY,      -- случайный (напр. hex(6)), непредсказуемый
    token_hash      TEXT NOT NULL,         -- sha256 hex сырого токена, НЕ сам токен
    scope           TEXT NOT NULL,         -- csv из {gmail,calendar,drive,sheets,docs,ticktick} ИЛИ буквально "all"
    label           TEXT,                  -- необязательно
    created_at      BIGINT NOT NULL,       -- unix ms
    expires_at      BIGINT NOT NULL,       -- created_at + 24ч (настраиваемо)
    revoked_at      BIGINT,                -- NULL, пока активно
    created_by_chat TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS tg_automation_windows_scope_idx
    ON tg_automation_windows (revoked_at, expires_at);
```

Канонические имена сервисов для `scope` — ровно так, строчными:
`gmail`, `calendar`, `drive`, `sheets`, `docs`, `ticktick`.

**Миграция с прежней схемы** (у ticktick-mcp уже есть эта таблица со
столбцом `server`, а не `scope` — влито 2026-08-10/11, боевая база):
`ALTER TABLE tg_automation_windows ADD COLUMN IF NOT EXISTS scope TEXT;
UPDATE tg_automation_windows SET scope = server WHERE scope IS NULL;` —
столбец `server` не трогать/не удалять (старые строки читаются, ничего не
теряется; DROP COLUMN на боевой таблице — не в этом ТЗ). И gmail-mcp, и
ticktick-mcp должны применять эту же идемпотентную миграцию при старте (та
же дисциплина, что у остальных таблиц этого слоя — `CREATE TABLE IF NOT
EXISTS`/`ADD COLUMN IF NOT EXISTS`, никогда не полагаться на то, что другой
сервис её уже применил первым).

**Проверка `scope` со стороны читающего сервиса** (например ticktick-mcp,
имя сервиса = `"ticktick"`): окно подходит, если `revoked_at IS NULL AND
expires_at > now()` И (`scope = 'all'` ИЛИ `'ticktick'` есть среди значений,
разбитых по запятой, — точное совпадение токена после split, НЕ `LIKE
'%ticktick%'`, чтобы гипотетический `ticktick2` не совпал по подстроке).

## gmail-mcp — интерактивный флоу (реализуется там)

1. Точка входа — команда `/automation_key` (текстом). Вебхук уже слушает
   только `callback_query`; для этой ОДНОЙ команды `allowed_updates`
   расширяется на `message` (тот же owner-only `chat_id`-чек, что и везде;
   `registerWebhook` — искать в `src/tg_approval.ts:468` — единственное
   место, где меняется набор).
2. Ответ на команду — сообщение с 8 инлайн-кнопками: 6 сервисов (каждая
   подписана `✗ gmail` / `✗ calendar` / ... изначально), `✗ Все сразу`,
   `Получить ключ`.
3. Нажатие на кнопку сервиса — переключает её же `✗`↔`✓` РЕДАКТИРОВАНИЕМ
   ТОГО ЖЕ сообщения (`editMessageReplyMarkup`/`editMessageText`), состояние
   выбора кодируется В САМОМ `callback_data` каждой кнопки (например
   `ak:toggle:gmail:101000` — где `101000` это битовая маска остальных пяти
   плюс сама эта позиция после переключения) — НЕ нужен отдельный сервер-сайд
   стейт/таблица для "текущего незавершённого выбора": вся нужная информация
   уже лежит в кнопках самого сообщения, Telegram её и хранит между
   нажатиями.
4. `✗ Все сразу` — переключает СРАЗУ все 6 в `✓` (или обратно в `✗`, если
   уже все выбраны — тоггл).
5. `Получить ключ` — разбирает текущую маску из своего `callback_data`,
   если ничего не выбрано — отвечает `answerCallbackQuery` текстом ошибки
   ("сначала отметь хотя бы один сервис"), ничего не генерирует. Если
   выбрано — генерирует токен (`crypto.randomBytes`/эквивалент), кладёт
   ХЭШ строкой в `tg_automation_windows` (`scope` — csv отмеченных имён,
   или `"all"`, если отмечены все 6 — эквивалентно, но `"all"` короче и
   читаемее в отчётах), отправляет владельцу ОТДЕЛЬНЫМ сообщением сырой
   токен + `scope` человеческим текстом ("действует на: ticktick, gmail").
6. Сообщение с токеном самоудаляется через 10с (`setTimeout` +
   `deleteMessage`, тот же принцип, что уже есть в ticktick-mcp —
   `schedule_message_delete`/`sweep_scheduled_deletes` в `tg_approval.py`,
   портировать логику на TS, не копировать код 1:1 раз стек другой).
7. Отдельно — `/automation_key list` (текст) и `/automation_key revoke <id>`
   (текст) / кнопка "Отозвать" на каждой строке списка — та же логика, что
   уже есть в ticktick-mcp (`list_windows`/`revoke_window`/
   `revoke_all_windows`), портировать на TS под новую таблицу (с `scope`,
   не с `server`).

## ticktick-mcp — только проверка (реализуется здесь, в этом воркдире)

1. `ticktick_mcp/src/automation_key.py`: заменить одно-серверную модель на
   scope. `find_window`/`check_window` — SQL ищет по `revoked_at IS NULL
   AND expires_at > now()`, затем в Python фильтрует по scope (`scope ==
   'all' or 'ticktick' in scope.split(',')`) — на активных строк обычно
   единицы, лишний SQL-парсинг CSV не нужен, простой Python-фильтр после
   выборки достаточен и читаемее, чем `string_to_array` в SQL.
2. Убрать/выключить у ticktick-mcp СОБСТВЕННУЮ генерацию/отзыв/список по
   кнопке (`/automation_key` в `tg_approval.py`, добавленный в
   `TZ_multi_automation_windows.md`) — теперь этим владеет только gmail-mcp.
   `matches_static`/статический `AUTOMATION_KEY` (env) — НЕ трогать, это
   отдельный, не связанный с этим ТЗ канал.
3. Миграция схемы — `ADD COLUMN IF NOT EXISTS scope`, бэкафилл из `server`
   (см. общую схему выше). Столбец `server` оставить как есть.
4. `_automation_key_channel` (`server.py`) — метка канала для аудита при
   совпадении по scope-окну остаётся `"window:<created_at>"`, без изменений
   по существу.

## Тестовый план (ticktick-mcp сторона)

1. Окно с `scope='ticktick'` — валидно для ticktick-mcp.
2. Окно с `scope='all'` — валидно для ticktick-mcp.
3. Окно с `scope='gmail,calendar'` (ticktick НЕ входит) — НЕ валидно для
   ticktick-mcp.
4. Окно с `scope='ticktick2'` (похожая, но другая строка) — НЕ валидно
   (точное совпадение токена после split, не подстрока).
5. Старая строка (мигрированная из `server='ticktick'`, `scope` = бэкафилл)
   — по-прежнему валидна после миграции.
6. Собственная генерация/отзыв/список по кнопке в ticktick-mcp — команда
   `/automation_key` либо убрана, либо явно отвечает "генерация теперь
   через gmail-mcp" (не создаёт строк сама).

## Явно НЕ входит в этот заход

- calendar-mcp, drive-mcp, sheets-mcp, docs-mcp (сторона проверки) —
  отдельная работа следом, тем же паттерном, что ticktick-mcp здесь.
- Удаление старого столбца `server` — не сейчас, не критично, лишний риск
  на боевой таблице без пользы.
