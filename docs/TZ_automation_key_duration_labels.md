# ТЗ-аддендум: настраиваемый срок, названия ключей, менеджер

**Статус:** уточнение владельца 2026-08-11, поверх `docs/TZ_automation_key_hub.md` и `docs/TZ_automation_key_miniapp.md` (обе уже в проде).

## 1. Настраиваемый срок жизни

Сейчас окно всегда живёт `AUTOMATION_WINDOW_HOURS` (фиксировано, дефолт 24ч
в старом коде). Владелец хочет выбирать при каждой генерации:
- конкретное число часов/дней/недель/месяцев;
- ИЛИ «бессрочно» (никогда не истекает).

**По умолчанию — 3 часа** (владелец явно поправил себя с «час» на «три
часа» — 3 часа, не 1).

### Схема

`tg_automation_windows.expires_at` — был `BIGINT NOT NULL`. Меняется на
**nullable**: `NULL` = бессрочно, число = unix ms истечения (как раньше).
`ALTER TABLE tg_automation_windows ALTER COLUMN expires_at DROP NOT NULL` —
идемпотентно (повторный `DROP NOT NULL` на уже nullable-колонке не падает).

Везде, где раньше было `expires_at > now`, становится `(expires_at IS NULL
OR expires_at > now)` — И в записи (gmail-mcp, создатель), И в чтении
(ticktick-mcp и любой другой сервис, который проверяет scope).

### Мини-апп (gmail-mcp)

Элемент выбора срока: число + единица (часы/дни/недели/месяцы) +
чекбокс/переключатель «Бессрочно» (при включении число+единица
дизейблятся). Дефолт при загрузке страницы — 3 часа. Отправляется в
`POST /automation-key-app/generate` как ещё одно поле (например
`durationMs: number | null`, `null` = бессрочно — переводить единицы в
миллисекунды на фронтенде, backend получает готовое число или `null`,
дополнительно валидирует разумные границы: не отрицательное, не абсурдно
маленькое типа 0).

### Бот (кнопки)

Полноценный выбор (число + единица) кнопками — избыточно. Вместо этого:
ПОСЛЕ нажатия «Получить ключ» (с уже отмеченными сервисами) бот показывает
ВТОРОЙ экран — быстрый выбор срока кнопками: `1 час`, `3 часа` (дефолт,
как-то отметить визуально, что это дефолт — например жирным в подписи),
`24 часа`, `7 дней`, `30 дней`, `Бессрочно`. Нажатие любой — генерирует
немедленно с этим сроком. Без окна выбора (нажал «Получить ключ» без
второго шага) — код НЕ должен молча генерировать с дефолтом за владельца:
второй экран — обязательный шаг, не пропускаемый.

**Кодирование выбора без сервер-side состояния** (тот же принцип, что и
маска сервисов): маска отмеченных сервисов из первого экрана переносится в
`callback_data` кнопок ВТОРОГО экрана целиком (например
`ak:gen:<mask>:<durationIndex>`), так что генерация на втором экране знает
и сервисы, и выбранный срок из ОДНОГО нажатия — никакого хранения «что
выбрано между двумя апдейтами» ни в памяти, ни в базе.

## 2. Названия ключей (label)

Колонка `label` уже существует в схеме (была задумана для этого с самого
начала, просто не подключена ни к одному UI). Теперь:

**Мини-апп** — текстовое поле «Название (необязательно)» на странице,
отправляется вместе с остальным в `POST /automation-key-app/generate`,
пустая строка → `null` (как и раньше было в схеме — `label TEXT`
nullable).

**Бот** — В ЭТОМ ЗАХОДЕ НЕ РЕАЛИЗУЕТСЯ (свободный текст плохо ложится на
чисто-кнопочный флоу без сервер-side состояния «жду ответа на этот
конкретный запрос генерации» — усложнение, которое владелец явно не
попросил безусловно, только как аналогию с API-ключами). Ключи,
сгенерированные через бот, остаются с `label = NULL` — в списке они
показываются просто по `window_id` и сроку/скоупу, без имени. Если позже
понадобится — отдельная работа.

## 3. Менеджер — список ВСЕХ ключей, не только активных

Сейчас `/automation_key list` (и его аналог в мини-аппе, если есть) —
показывает ТОЛЬКО активные окна (`revoked_at IS NULL AND expires_at >
now`), истёкшие/отозванные исчезают из виду полностью. Владелец хочет
видеть картину целиком: какие ещё живы, какие уже истекли, какие отозваны
вручную — со статусом у каждого.

### Что показывать по каждой строке
- `window_id` (или его короткий кусок — то, что уже используется для
  `ak:revoke:<id>` кнопок);
- `label`, если есть (иначе просто без имени, не «(без названия)» текстом
  — молча пропустить эту часть строки);
- `scope` (человекочитаемо — те же имена, что в кнопках выбора: «gmail,
  ticktick» или «все»);
- статус — один из: `✅ активен (осталось Xч)` / `⌛ истёк <когда>` /
  `🚫 отозван <когда>` / `♾ бессрочно` (для `expires_at IS NULL`, пока не
  отозван).

### Разумные пределы
Список ВСЕХ когда-либо выданных ключей может стать длинным (владелец сам
будет генерировать их часто, судя по описанному сценарию — «выдал на этот
чат», «на тот чат»). Ограничить последними N (например 30, самые свежие
сверху) с явной строкой «показаны последние 30 из M» — та же дисциплина
"не скрывать усечение молча", что и везде в этой экосистеме проектов
(`docs/TZ/ZAHOD1.md` — "нет скрытых потолков без объявления", тот же
принцип, хоть это и другой репозиторий).

### Отзыв — без изменений по механизму
Кнопка «Отозвать» на каждой активной строке — как уже есть. У неактивных
строк (истёкшие/уже отозванные) кнопки «Отозвать» просто нет (нечего
отзывать).

## Тестовый план

1. Генерация с `durationMs=null` (мини-апп) → `expires_at IS NULL` в базе.
2. Генерация с конкретным сроком (например 7 дней в мс) → `expires_at =
   created_at + указанное`.
3. `find_window`-эквивалент (или что там читает окно на проверке) считает
   `expires_at IS NULL` окно ДЕЙСТВУЮЩИМ, не истёкшим.
4. Мини-апп: пустое поле названия → `label = NULL` в базе; заполненное →
   сохраняется как есть.
5. Бот: второй экран (выбор срока) показывается ПОСЛЕ выбора сервисов и до
   генерации; без выбора срока — генерация НЕ происходит (нет пропуска
   шага).
6. Бот: каждый из 6 пресетов срока (1ч/3ч/24ч/7д/30д/бессрочно) даёт
   правильный `expires_at`/`NULL`.
7. Список показывает И активные, И истёкшие, И отозванные — с правильным
   статусом у каждого, включая `label` и `scope`.
8. Список усекается на разумном числе с явной строкой об усечении, если
   реально выданных ключей больше лимита.
9. Регресс: существующие тесты (создание/scope/revoke/audit из прошлых
   заходов) остаются зелёными без изменений по существу — меняется только
   то, что напрямую относится к сроку/названию/списку.

## Явно НЕ входит

- Название (label) для ключей, выданных через бот — оставлено как открытый
  долг, не в этом заходе (раздел 2 выше).
- Изменение уже выданных, ныне действующих ключей (продление/переименование
  задним числом) — не запрашивалось.
