# ТЗ-аддендум: выдача ключа как self-destruct-заметка + постоянные точки входа

**Статус:** уточнение владельца 2026-08-11, поверх всех предыдущих аддендумов automation_key. Реализуется ПОСЛЕ `docs/TZ_automation_key_duration_labels.md` (те же файлы — избегаем конфликта параллельной правки).

## 1. Выдача ключа — self-destruct-заметка вместо голого текста

Владелец: «ключ пусть выдаётся сразу как self-destruct заметка — прямо в
мини-апп, если в мини-апп запрашиваешь, и в тг, если в тг запрашиваешь».

Использовать УЖЕ существующий сервис `self-destroyed-notes`
(`https://self-destroyed-notes-production.up.railway.app`) — тот же, которым
владелец сам пользуется для передачи секретов. Сервер этого сервиса
**никогда не видит ключ расшифровки** — шифрование происходит на
отправляющей стороне (тот же приём, что уже реализован в его собственном
коде для случая «через Telegram-бота»: `src/crypto.ts` файла
`self-destroyed-notes`, функции `generateKey()`/`encrypt()`, чистый
`node:crypto`, AES-256-GCM + PBKDF2-SHA256, БЕЗ внешних зависимостей —
скопировать эти ~35 строк byte-for-byte в gmail-mcp, портируемый модуль,
тот же принцип, что уже применён для `automation_key.ts`/`tg_approval.ts`
дублирования).

### Механизм (со стороны gmail-mcp)

1. `key = generateKey()` — `crypto.randomBytes(32).toString("base64url")`.
2. `payload = encrypt(rawAutomationToken, key)`.
3. `POST https://self-destroyed-notes-production.up.railway.app/api/notes`
   тело `{payload, oneView: true, ttl: 3600}` (час на то, чтобы открыть
   ссылку — сама выданная automation_key живёт своим сроком независимо,
   TTL здесь только про «сколько ссылка на заметку остаётся кликабельной
   ДО первого открытия», не про срок самого ключа) → ответ `{id}`.
4. Ссылка: `https://self-destroyed-notes-production.up.railway.app/#/n/<id>/<key>`.
5. ЭТУ ссылку показывать/отправлять вместо сырого токена — везде, где
   раньше был сырой токен в тексте сообщения/на странице мини-аппа.

### Где показывается

- **Бот (кнопки)**: сообщение с ссылкой вместо токена, та же дисциплина
  самоудаления сообщения через 10с, что и раньше (`schedule_message_delete`
  — переиспользовать, не менять таймер).
- **Мини-апп**: страница показывает ссылку (кликабельную, с кнопкой
  «Открыть заметку» или просто гиперссылкой) ПРЯМО НА СТРАНИЦЕ — не только
  «отправлено в чат» текстом, как было раньше. Отдельно ссылку можно
  ТАКЖЕ продублировать сообщением в чат (не обязательно, но и не запрещено
  — реши по месту, что аккуратнее; если решишь не дублировать в чат при
  запросе из мини-аппа — явно напиши это в финальном ответе, это
  сознательное архитектурное решение, не молчаливое упущение).

### Важно — не хардкодить секреты повторно

Никаких новых переменных окружения для этого сервиса не требуется — он
публичный (URL известен), создание заметки не требует аутентификации на
его стороне (см. `POST /api/notes` в его `src/server.ts` — берёт только
`payload`/`oneView`/`ttl`, ключа/токена доступа не спрашивает).

## 2. Постоянные точки входа — не только команда текстом

Владелец: «нужна кнопка на команду `/automation_key` в боте + кнопка для
мини-аппа, сделай по-людски».

### 2.1. `/automation_key` в автодополнении команд Telegram

Один вызов Telegram Bot API при старте сервера (там же, где уже
регистрируется вебхук, `registerWebhook`/аналог) —
`setMyCommands([{command: "automation_key", description: "Ключ для автоматики (временный/постоянный)"}])`
— тогда команда появляется в стандартном автодополнении при наборе `/` в
чате с ботом, не нужно печатать её вручную целиком по памяти.

### 2.2. Постоянная кнопка меню чата → сразу открывает мини-апп

`setChatMenuButton` (Telegram Bot API) с
`{type: "web_app", text: "Ключ", web_app: {url: "<mini-app URL>"}}` —
это ПОСТОЯННАЯ кнопка РЯДОМ С ПОЛЕМ ВВОДА СООБЩЕНИЯ (не в клавиатуре
чата, отдельный UI-элемент Telegram), открывает мини-апп В ОДНО КАСАНИЕ,
без всякой команды. Вызывается один раз при старте (идемпотентно — можно
звать на каждом старте сервера, Telegram просто переустановит то же самое,
без вреда).

Оба вызова (2.1 и 2.2) — best-effort при старте (как и `registerWebhook`
сейчас): не должны ронять запуск сервера при сбое, громко логировать
ошибку, если не получилось.

## Тестовый план

1. Ключ, выданный через бот — сообщение содержит URL вида
   `https://self-destroyed-notes-production.up.railway.app/#/n/`, НЕ содержит
   сырой токен automation_key напрямую в тексте.
2. Ключ, выданный через мини-апп — ответ backend'а/страница несёт ту же
   ссылку, не сырой токен.
3. `encrypt`/`generateKey` дают payload, который РЕАЛЬНО расшифровывается
   обратно тем же алгоритмом (тест на round-trip: зашифровать → расшифровать
   вручную в тесте тем же AES-256-GCM/PBKDF2 — не полагаться только на то,
   что "выглядит похоже на оригинал", а фактически проверить дешифровку).
4. `setMyCommands`/`setChatMenuButton` вызываются при старте (мокнуть
   `tgCall`, проверить, что оба метода реально позваны с ожидаемыми
   аргументами).
5. Сбой вызова `setMyCommands`/`setChatMenuButton` не роняет старт сервера
   (try/catch, лог ошибки, не исключение наружу).
6. Регресс — полный `npm test` зелёный.

## Явно НЕ входит

- Password-защита заметки (`pw`/второй фактор поверх ключа) — не
  запрошено, `encrypt()` поддерживает, но не используем здесь.
- Настройка TTL заметки владельцем — фиксированный час, не настраиваемо
  пользователем в этом заходе.
