# ТЗ: подтверждение гейтов в веб-интерфейсе — гибридное ожидание, единый хаб, уведомления macOS

**Статус:** задача владельца 2026-08-12, поверх завершённой ветки automation_key
(`TZ_automation_key_consent_gate.md`, `..._hub.md`, `..._miniapp.md`,
`..._note_delivery_and_buttons.md`, `..._method_catalog.md`).

## Зачем

Сейчас единственный интерактивный путь подтверждения — кнопка в Telegram.
Дословно от владельца: «в тг не супер удобно конечно это делать», нужен
веб-интерфейс с галочками, удобный И с телефона, И с 24" iMac. Плюс
отдельно: «проверка же может идти сразу при вызове метода в LLM и мне может
приходить уже проверенное» — то есть по возможности избавиться от второго
прохода модели. Плюс: нативные уведомления macOS о новых ожидающих
подтверждения действиях.

Telegram-кнопки НЕ убираются и НЕ меняются — веб становится вторым,
равноправным каналом. Это осознанное решение владельца (обсуждалось явно).

## Часть 1 — гибридное ожидание внутри вызова тула (`consent.ts`, все 5 репо)

### Проблема, которую решаем

Сейчас: вызов тула → план → превью модели → (человек подтверждает где-то) →
СЛЕДУЮЩИЙ вызов тула исполняет. Два прохода модели. Полностью синхронное
ожидание (висеть до подтверждения) не годится — MCP-клиенты режут долгие
вызовы по таймауту, план потеряется.

### Решение

После создания манифеста, ДО возврата превью, `requireConsent` опрашивает
собственный стор: не подтвердил ли человек этот манифест прямо сейчас.

```
const deadline = now() + cfg.syncWaitMs;      // 0 ⇒ фича выключена целиком
while (now() < deadline) {
  await sleep(cfg.syncPollMs);                 // ~1000мс
  const row = await store.getConsentManifest(manifestId);
  if (!row || row.status !== "AWAITING_CONSENT") break;   // решено или исчезло
  ...
}
```

Исходы:
1. **Подтверждено в окне ожидания** — идём тем же путём, что и обычная фаза
   исполнения: обязательный `rehash()`/binding-чек (НЕ пропускать — тот же
   принцип, что уже в automation_key-ветке), аудит-запись, исполнение,
   возврат `{kind: "confirmed", ...}` — модель получает готовый результат
   ОДНИМ вызовом.
2. **Отклонено в окне ожидания** — `{kind: "refused"}` с тем же текстом
   отказа, что и на обычном пути.
3. **Дедлайн истёк, статус всё ещё AWAITING_CONSENT** — возвращаем ОБЫЧНОЕ
   превью (`{kind: "planned"}`), как сегодня. Ничего не потеряно, дальше
   работает уже существующий асинхронный путь (Telegram/веб/следующий вызов
   модели). Это НЕ ошибка и НЕ таймаут наружу.

### Конфигурация

- `CONSENT_SYNC_WAIT_MS` — сколько ждать. Дефолт **25000** (25с — с запасом
  под типовой ~60с таймаут MCP-клиента, включая время самого `plan()`).
  `0` ⇒ ожидание выключено целиком, поведение побайтово как сегодня.
- `CONSENT_SYNC_POLL_MS` — интервал опроса, дефолт **1000**.
- Оба читаются тем же приёмом, что уже читаются `sendBatchMax`/`ttl`-настройки
  в `config.ts` каждого сервиса (посмотри и следуй существующему стилю).

### Дисциплина

- Опрос — ТОЛЬКО чтение собственного стора (`getConsentManifest`), никаких
  новых внешних вызовов/HTTP из `consent.ts`.
- Binding-чек (`rehash`) обязателен и на этом пути — план мог устареть даже
  за 25 секунд.
- `syncWaitMs === 0` ⇒ ни одного лишнего запроса к БД, ни одной задержки —
  ветка не существует.
- Не ломать automation_key-ветку: она проверяется РАНЬШЕ и, если сработала,
  до ожидания дело не доходит вовсе.

## Часть 2 — единый веб-хаб подтверждений

### Где живёт

Хаб — в gmail-mcp (как и automation_key-хаб). ОДНА адаптивная HTML-страница,
доступная двумя путями:
- `GET /consent-hub/<CONSENT_HUB_SECRET>` — прямая ссылка, открывается в
  любом браузере (телефон, iMac), без Telegram;
- та же страница как `web_app`-кнопка бота (`setChatMenuButton`/кнопка в
  меню `/automation_key` — добавь пункт, не ломая существующие) — тогда её
  рендерит Telegram в своём узком окне.

Одна разметка, никакого дублирования кода под мобильный и десктоп: адаптив
через `@media (min-width: 760px)`.

### Раскладка (макеты согласованы с владельцем)

**Узкий экран (<760px):** список карточек — чекбокс, точка-цвет сервиса, имя
сервиса, заголовок действия, сжатая сводка, время. Тап по телу карточки
разворачивает полный текст превью прямо в списке + три кнопки: «Подтвердить»,
«Отклонить с комментарием», «Отклонить».

**Широкий экран (≥760px):** двухколоночная раскладка — слева тот же список
(уже, компактнее, без разворота), справа постоянная панель чтения с полным
текстом выбранного пункта и теми же тремя кнопками. Первый пункт выбран по
умолчанию.

**Массовый отбор (обе раскладки):** чекбоксы отмечают пункты, снизу
появляется липкая панель «Выбрано: N» + кнопка «Проверить и подтвердить».
Она открывает ФИНАЛЬНЫЙ экран со списком отмеченного, и только там — кнопка
«Подтверждаю N действий». Галочка сама по себе НИЧЕГО не подтверждает —
это принципиально (нельзя подтвердить пачку не глядя).

**Фильтр** — чипы по сервисам со счётчиками («Все · 5», «Gmail · 2», …).

Готовый рабочий прототип разметки/логики (адаптив, разворот, панель чтения,
массовый отбор, финальный экран) лежит в
`scratchpad/consent_web_demo.html` — бери его как отправную точку разметки и
CSS, не изобретай с нуля. Данные там демонстрационные, замени реальными.

«Отклонить с комментарием» — раскрывает текстовое поле; введённый текст
уходит как `userReply` (тот же путь, что и человеческая реплика из Telegram),
модель увидит его и сможет перестроить план.

### Backend

**В КАЖДОМ из 5 сервисов** (gmail/calendar/drive/sheets/docs-mcp):

1. `GET /pending-consents` — список СВОИХ манифестов в статусе
   `AWAITING_CONSENT` (не истёкших). Ответ:
   ```json
   {"service": "gmail", "items": [
     {"manifestId": "...", "tool": "gmail_send", "title": "...",
      "summary": "...", "preview": "...", "createdAt": 1234567890,
      "expiresAt": 1234567890, "accountLabel": "personal"}
   ]}
   ```
   `title`/`summary` — короткие человеческие строки для списка; `preview` —
   полный текст, тот же, что уходит в Telegram/модели. Если в сторе сейчас
   нет отдельных коротких полей — выведи их из уже имеющегося превью
   (первая строка как title, вторая как summary) и явно отметь это решение
   в отчёте, не выдумывай новых колонок в БД без нужды.

2. `POST /pending-consents/decide` — тело
   `{manifestId, decision: "confirm" | "reject", comment?: string}`.
   - `confirm` → идёт РОВНО тем же путём, что нажатие кнопки в Telegram
     (найди, как это сделано сейчас — `tryAutoExecute`/`executeApproved*` —
     и переиспользуй, не дублируй логику): binding-чек, аудит, исполнение.
   - `reject` → тот же путь отказа, `comment` (если есть) записывается как
     `userReply`.
   - Ответ: `{ok: true, outcome: "confirmed"|"refused", result?: string}` или
     понятный 4xx с машиночитаемым `error` (`not_found`, `already_decided`,
     `binding_mismatch`, `expired`) — НИКОГДА 500 на предсказуемых причинах.

3. **Авторизация обоих роутов** — общий секрет `CONSENT_HUB_SECRET` (одна и
   та же строка во всех 5 сервисах, как уже сделано для статического
   `AUTOMATION_KEY`), передаётся заголовком `X-Consent-Hub-Secret`.
   Сравнение — константное по времени (`timingSafeEqual`), как везде в этой
   экосистеме. Секрет не задан ⇒ оба роута отвечают 404 (фича выключена,
   fail-closed, НЕ открытый доступ).

**В gmail-mcp дополнительно** (хаб):
4. `GET /consent-hub/<secret>` — сама страница. Секрет в пути, как у уже
   существующего `/dashboard/<secret>` — следуй тому же приёму (включая
   маскирование секрета в логах, оно там уже реализовано).
5. `GET /consent-hub-api/pending` — агрегатор: параллельно ходит на
   `/pending-consents` СВОЙ и четырёх соседей (URL-ы уже есть —
   `loadExternalCatalogUrls` в `config.ts`, переиспользуй), склеивает,
   возвращает единым списком с полем `service` у каждого пункта.
   Недоступность одного сервиса НЕ роняет весь ответ — этот сервис
   помечается как недоступный, остальные показываются (та же деградация,
   что уже сделана для каталога методов).
6. `POST /consent-hub-api/decide` — прокси на нужный сервис по `service`
   пункта, добавляя `X-Consent-Hub-Secret`. Браузер секрета НЕ ВИДИТ вообще
   (кроме того, что в URL страницы) — все межсервисные вызовы делает сервер.

### Что НЕ трогать

- Telegram-путь (кнопки, `tg_approval.ts`) — ни строкой.
- Сам `requireConsent`, кроме Части 1.
- Формат/схему `consent_manifests` — если для `title`/`summary` не хватает
  данных, выводи их из превью, а не мигрируй таблицу.

## Часть 3 — уведомления macOS

Локальный демон на машине владельца (НЕ в репозиториях MCP-серверов —
отдельная папка, например `~/.local/share/consent-notifier/`, либо новый
маленький репозиторий, реши по месту и укажи в отчёте).

1. Скрипт (bash или Node — на твой выбор, обоснуй) раз в N секунд (дефолт
   30) ходит на `GET /consent-hub-api/pending` с секретом, сравнивает набор
   `manifestId` с сохранённым на диске (`~/.local/state/consent-notifier/
   seen.json` или аналог) и на КАЖДЫЙ новый шлёт уведомление:
   ```
   terminal-notifier -title "Gmail · отправить письмо" \
     -message "Eric — «Смета на август»" \
     -open "https://gmail-mcp-production-.../consent-hub/<secret>"
   ```
   (`terminal-notifier` — выбор владельца, ставится `brew install
   terminal-notifier`; клик по уведомлению открывает страницу подтверждения).
2. `LaunchAgent`-plist (`~/Library/LaunchAgents/`) для автозапуска при
   логине — **НАПИСАТЬ ФАЙЛ, НО НЕ ЗАГРУЖАТЬ** (`launchctl load` НЕ
   выполнять): это постоянная конфигурация автозапуска на машине владельца,
   он загрузит сам после проверки. В отчёте — точная команда, которой он это
   сделает.
3. Секрет НЕ хардкодить в скрипт: читать из файла с правами `600`
   (`~/.config/consent-notifier/env` или аналог), путь указать в отчёте.
   Не печатать секрет ни в логи, ни в уведомления.
4. Уже виденные и уже решённые манифесты не должны уведомлять повторно —
   состояние на диске, чистится от исчезнувших id (иначе файл растёт вечно).

## Тестовый план

**Часть 1** (в каждом из 5 репо):
1. `syncWaitMs = 0` — поведение побайтово как раньше, весь существующий
   набор тестов зелёный без правок.
2. Манифест подтверждён «человеком» в середине окна ожидания (мок-стор
   меняет статус на 2-й итерации опроса) — тул возвращает `confirmed` с
   первого вызова, БЕЗ превью, мутация реально произошла.
3. Манифест отклонён в окне — `refused`, мутации нет.
4. Никто ничего не сделал за окно — обычное превью (`planned`), ровно то же,
   что вернулось бы без фичи; после этого обычный второй вызов с
   `manifest_id`+`user_reply` по-прежнему работает (регресс).
5. Binding-чек срабатывает и на sync-пути: `rehash` вернул другой хеш —
   отказ, не тихое исполнение.
6. automation_key + sync одновременно: валидный ключ исполняет СРАЗУ, до
   ожидания, ни одной итерации опроса не происходит.

**Часть 2:**
7. `GET /pending-consents` без секрета / с неверным секретом — 404 (не 401 и
   не 403: не подтверждаем существование роута).
8. `CONSENT_HUB_SECRET` не задан — оба роута 404, остальной сервис работает.
9. `decide confirm` — реально исполняет (мутация произошла), повторный
   `decide` на тот же манифест — `already_decided`, второй мутации НЕТ.
10. `decide reject` с комментарием — манифест отклонён, комментарий записан
    как `userReply` в аудит.
11. Агрегатор: один из соседей недоступен — остальные пункты отдаются,
    сбойный сервис помечен, ответ 200, не 500.
12. Страница: узкий viewport — карточки с разворотом; широкий — две колонки
    с панелью чтения (проверить реальным HTTP-запросом + разбором разметки,
    не «на глаз»).

**Часть 3:**
13. Демон: новый манифест → ровно одно уведомление; тот же манифест на
    следующей итерации → уведомления НЕТ; исчезнувший манифест вычищается
    из состояния.
14. Секрет не попадает ни в лог демона, ни в текст уведомления.

**Общее:** полный `npm test` каждого репо зелёный, число тестовых файлов
до/после — посчитать и указать.

## Явно НЕ входит

- ticktick-mcp (Python, отдельная архитектура) — в этом заходе не трогаем,
  его гейт остаётся только в Telegram.
- Замена/отключение Telegram-кнопок.
- Push-уведомления через браузер (Web Push) — вместо них локальный демон.
- Аутентификация хаба чем-то серьёзнее общего секрета (OAuth/пароль) — не
  запрошено, секрет в URL + серверный проброс достаточен для одного
  владельца.
