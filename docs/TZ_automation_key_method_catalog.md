# ТЗ: automation_key — выбор ПО МЕТОДАМ, а не только по сервисам, через автосправочник

**Статус:** задача владельца 2026-08-11, поверх уже завершённого
`TZ_automation_key_consent_gate.md` (гейт во всех 5 TS-сервисах) и
`TZ_automation_key_note_delivery_and_buttons.md` (доставка ключа заметкой).

## Контекст и требование владельца

Дословно: «давай сразу пилить возможность выбора методов, причём
архитектурно нужно сделать так, чтобы при добавлении гейтированного метода —
он автоматом добавлялся, то есть в целом добавление метода идёт через
справочник».

Значит ДВЕ вещи одновременно:
1. Ключ теперь можно выпускать со scope не только «весь `gmail`», но и
   «только `gmail_send` и `gmail_reply`».
2. Список доступных для выбора методов НИГДЕ не хранится руками — при
   добавлении нового гейтированного тула (новый `server.registerTool(...)`
   с `requireConsent` внутри) он появляется в списке сам, без правки
   бота/мини-аппа/справочника кем-либо.

## Разведка (уже сделана, см. отчёт агента-исследователя)

- Тулы регистрируются через `@modelcontextprotocol/sdk`'s `McpServer.
  registerTool(name, {title, description, inputSchema, annotations}, handler)`.
- У SDK есть штатный, публичный, протокольный способ получить список
  зарегистрированных тулов ВМЕСТЕ с их JSON-схемой параметров — запрос
  `tools/list`. Его можно вызвать В ПАМЯТИ процесса (не по сети), создав
  связанную пару транспортов через `InMemoryTransport.createLinkedPair()`
  (штатная утилита самого SDK, используется в его собственных тестах) —
  подключить лёгкий `Client` к уже собранному `McpServer` и позвать
  `client.listTools()`. Это даёт официальный, протокольно-гарантированный
  список — НЕ чтение приватного поля `_registeredTools` (оно физически
  доступно, но не публичный контракт SDK, ломкое на апдейтах — НЕ
  использовать, только `InMemoryTransport` + `listTools()`).
- Каждый гейтированный тул уже ОБЯЗАН (по `TZ_automation_key_consent_gate.md`)
  нести Zod-параметр `automation_key` в своей схеме. Значит определение
  «гейтирован» ⟺ «`inputSchema.properties.automation_key` присутствует в
  JSON-схеме, отданной `tools/list`» — точное, автоматическое, без единого
  ручного списка где бы то ни было.
- Если в установленной версии SDK `InMemoryTransport` почему-то недоступен —
  зафиксируй это явно в отчёте и обоснуй, каким запасным путём ты получил
  список (не молчаливый фоллбэк на приватные поля без объяснения).

## Что делать в КАЖДОМ из пяти сервисов (gmail/calendar/drive/sheets/docs-mcp)

### 1. Новый модуль каталога — например `src/gated_tools_catalog.ts`

Экспортирует асинхронную функцию (сигнатуру подбери по месту, например
`listGatedTools(server: McpServer): Promise<{name: string; description: string}[]>`):
1. Поднимает `InMemoryTransport.createLinkedPair()`, соединяет с уже
   собранным `server` (в каждом репо есть функция вроде `buildMcpServer(user)`
   — используй тот же путь построения, что и обычный вызов, посмотри, нужен
   ли синтетический/заглушечный `user`, если список тулов НЕ зависит от
   конкретного пользователя — если списки тулов ЗАВИСЯТ от `user` (проверь
   по коду), явно опиши это ограничение в отчёте: каталог тогда отражает
   набор тулов для «типового» пользователя, а не персональный).
2. Зовёт `client.listTools()`.
3. Фильтрует на `tool.inputSchema.properties?.automation_key !== undefined`.
4. Возвращает `{name, description}[]` (description — короткое, из самого
   тула; если слишком длинное для UI — можно обрезать разумно, отметь в
   отчёте, если обрезаешь).
5. Закрывает соединение/транспорт после использования (не течёт).

### 2. Новый HTTP-роут — `GET /automation-key-catalog`

Рядом с существующим `/automation-key-app` в `http.ts`. Без авторизации
(список ИМЁН методов не секрет — тот же принцип, что и сам `tools/list` по
факту доступен любому, кто прошёл MCP-авторизацию; здесь даже без нее, т.к.
имена методов не являются чувствительными данными). Отдаёт:
```json
{"service": "<канонiческое_имя_сервиса>", "tools": [{"name": "...", "description": "..."}]}
```
Канонические имена сервисов — те же, что уже используются в `scope`:
gmail/calendar/drive/sheets/docs/ticktick (`AUTOMATION_SERVICE`-константа,
уже есть в каждом репо из прошлого захода).

### 3. Расширение формата `scope`

Сейчас: CSV из имён сервисов ИЛИ литерал `"all"`. Расширяем токены CSV до:
- `all` — всё (без изменений);
- `<service>` — ВСЕ методы этого сервиса (без изменений, обратная
  совместимость — уже выпущенные окна с таким scope продолжают работать
  ровно как раньше, ничего не мигрировать в БД);
- `<service>:<tool_name>` — НОВОЕ, конкретный один метод.

Обнови `scopeCovers`/аналог (сейчас сверяет только `service`) до сигнатуры
`scopeCovers(scope: string, service: string, tool: string): boolean`:
```ts
function scopeCovers(scope: string, service: string, tool: string): boolean {
  if (scope === "all") return true;
  const tokens = scope.split(",").map(t => t.trim()).filter(Boolean);
  return tokens.some(t => t === service || t === `${service}:${tool}`);
}
```
Точное сравнение токенов (`===`), НЕ подстрока и НЕ `startsWith` — та же
дисциплина, что уже проверена тестом «`google-sheets` не матчит `sheets`»:
теперь дополнительно нужен тест «`gmail:gmail_send` НЕ матчит
`gmail:gmail_send_all`» (или подобная пара с общим префиксом).

### 4. `checkAutomationKey` — прокинуть `tool`

Сигнатура меняется с `(key: string) => Promise<{ok, channel}>` на
`(key: string, tool: string) => Promise<{ok, channel}>` — ВЕЗДЕ (портируемый
`consent.ts`, `RequireConsentParams.checkAutomationKey`, и конкретная
реализация в `automation_key.ts`/`automationKeyCheck.ts` каждого сервиса).

В `consent.ts` вызов уже находится внутри `requireConsent`, где параметр
`tool` (имя текущего инструмента) УЖЕ существует как часть
`RequireConsentParams` — просто прокинь его вторым аргументом:
`await p.checkAutomationKey(p.automationKey, tool)`. Ни один вызывающий
инструмент (`src/tools/*.ts`) менять не нужно — они передают
`checkAutomationKey` как ссылку на функцию, не вызывают её сами.

Реализация проверки внутри каждого сервиса (там, где сейчас сверяется
`scope`) — передать этот `tool` в `scopeCovers(row.scope, MY_SERVICE, tool)`
вместо старого `scopeCovers(row.scope, MY_SERVICE)`.

## Что делать ТОЛЬКО в gmail-mcp (хаб UI)

### 5. Бот — НЕ пытаться впихнуть методы в inline-кнопки

Telegram ограничивает `callback_data` 64 байтами — кодировать битовую маску
на десятки методов туда физически нельзя (уже используемый трюк
"состояние в callback_data" работал для 6 сервисов, не масштабируется на
~60+ методов). Решение: бот остаётся как есть (грубый выбор по сервисам,
уже реализовано) — ДОБАВЬ одну дополнительную кнопку на первом экране
выбора сервисов: «🎯 Точнее — по методам (открыть в мини-аппе)» —
открывает тот же мини-апп (`web_app` кнопка, как уже есть в
`registerBotUiEntryPoints`), без выбора в самом боте.

### 6. Мини-апп — дерево «сервис → методы»

`src/automation_key_miniapp.ts`, страница генерации:
1. При загрузке страницы — параллельные `fetch` на `/automation-key-catalog`
   каждого из пяти сервисов (URL-ы сервисов уже известны — там же, где сейчас
   вообще решается, какие сервисы существуют для чекбоксов; ticktick-mcp
   ИСКЛЮЧЕНИЕ — у него нет этого HTTP-роута и не будет в этом заходе, он
   продолжает работать только на уровне целого сервиса, `scope` для него —
   всегда просто `"ticktick"`, без методов; явно отметь это в UI, не пытайся
   получить его каталог).
2. Рендер: чекбокс сервиса (как сейчас, «выбрать всё») + под ним
   раскрывающийся список чекбоксов методов этого сервиса (из каталога).
   Если сервис-каталог недоступен (сеть/сервис лежит) — не ронять всю
   страницу, деградировать до старого поведения (только чекбокс всего
   сервиса), с видимой пометкой «методы недоступны, выдам доступ на весь
   сервис».
3. Сборка `scope` при отправке: если у сервиса выбран весь набор методов ИЛИ
   нажат чекбокс «весь сервис» — эмитить короткий токен `<service>`
   (обратная совместимость, компактность); если выбраны отдельные методы —
   эмитить `<service>:<tool>` на каждый выбранный метод.
4. `POST /automation-key-app/generate` — сейчас тело, видимо, кодирует
   выбор битовой маской по сервисам (посмотри текущий код). Переделай на
   передачу готового списка токенов scope (простой массив строк в теле
   запроса) — backend только валидирует формат токена (регулярка вида
   `^[a-z_]+(:[a-z0-9_]+)?$`, не более разумного числа токенов, скажем 200 —
   защита от мусора/DoS, не полноценная кросс-сервисная проверка "токен
   реально существует в каком-то каталоге" — заводить это НЕ обязательно в
   этом заходе, отметь как сознательно вне рамок, если не делаешь).

### 7. Обратная совместимость бота

Кнопочный флоу бота (без метода) продолжает эмитить старые токены-сервисы,
как раньше — ничего не меняется в его коде, кроме добавления одной кнопки
из п.5.

## Тестовый план (на каждый из пяти сервисов, где применимо)

1. `listGatedTools`/аналог — реальный прогон против собранного тестового
   сервера с хотя бы одним гейтированным и хотя бы одним НЕ гейтированным
   тулом (без `automation_key` в схеме) — в списке оказывается ТОЛЬКО
   гейтированный.
2. `GET /automation-key-catalog` — живой HTTP-вызов, ответ содержит ожидаемые
   имена (сверить с текущим списком `tool: "..."` в `requireConsent` вызовах
   этого репо — тем самым списком, который уже был найден разведкой для
   gmail-mcp).
3. `scopeCovers` — новые кейсы: `service:tool` матчит точно этот метод,
   НЕ матчит другой метод того же сервиса, НЕ матчит общий префикс без `:`
   (`gmail:gmail_send` vs `gmail:gmail_send_extra`), bare `service` по
   прежнему покрывает любой метод (обратная совместимость), `all` покрывает
   всё.
4. `checkAutomationKey(key, tool)` — валидный ключ с scope на КОНКРЕТНЫЙ
   метод пропускает вызов именно этого метода и НЕ пропускает вызов другого
   гейтированного метода того же сервиса (это ключевой новый тест —
   до этого захода такого разграничения не было вообще).
5. Регресс — существующие окна с bare-service scope (без правки в БД)
   по-прежнему работают на ЛЮБОЙ метод своего сервиса.
6. (gmail-mcp только) Мини-апп: страница реально запрашивает 4 внешних
   каталога (calendar/drive/sheets/docs) + собственный, деградирует на сбое
   одного из них без падения всей страницы; отправленный `scope` содержит
   ожидаемые токены для смешанного выбора (часть сервисов целиком, часть —
   по методам).
7. Полный `npm test` репозитория зелёный, ничего старого не сломано.

## Явно НЕ входит

- ticktick-mcp — у него отдельная архитектура на Python, каталог методов
  туда в этом заходе не добавляется, `scope="ticktick"` остаётся
  единственным доступным токеном для него.
- Полная кросс-сервисная серверная валидация "токен из тела запроса реально
  существует в каком-то каталоге" на бэкенде мини-аппа — только
  формат-валидация регуляркой (см. п.6 раздела про хаб).
- Password/доп. защита заметки — не относится к этому ТЗ (было решено
  раньше, отдельно).
